# コードレビュールール

本ドキュメントでは、プルリクエスト（PR）のレビュー基準と手順を定めています。高品質なコードベースを維持し、チーム全体の知識共有を促進することを目的としています。

## コードレビューの目的

コードレビューは以下の目的で実施します:

1. **品質の向上**: バグや潜在的な問題を早期に発見
2. **知識の共有**: チーム全体でコードベースの理解を深める
3. **学習の機会**: ベストプラクティスやテクニックを学び合う
4. **一貫性の維持**: コーディング規約やアーキテクチャの統一
5. **セキュリティの確保**: 脆弱性やセキュリティリスクの検出

## プルリクエストの作成

### PR を作成する前のチェックリスト

- [ ] コードが正常に動作することを確認
- [ ] テストが追加され、すべてパスしている
- [ ] Biome のチェックがパスしている（`pnpm biome:check`）
- [ ] 不要なコメントやデバッグコードが除かれている
- [ ] 自己レビューを実施し、明らかな問題を修正済み

### PR のタイトル

PR のタイトルは以下の形式で記述します:

```
[種別] 簡潔な説明
```

**種別の例**:

- `[Feature]`: 新機能の追加
- `[Fix]`: バグ修正
- `[Refactor]`: リファクタリング
- `[Docs]`: ドキュメントの更新
- `[Test]`: テストの追加・修正
- `[Chore]`: ビルド設定、依存関係の更新など

**例**:

```
[Feature] ドキュメント作成機能の実装
[Fix] ログインフォームのバリデーションエラーを修正
[Refactor] ユーザーリポジトリの処理を整理
```

### PR の説明

PR の説明には以下の内容を含めます:

````markdown
## 概要

この PR では〇〇を実装しました。

## 変更内容

- ✨ 新機能: ドキュメント作成フォームを追加
- 🐛 修正: バリデーションエラーを修正
- ♻️ リファクタリング: コンポーネントを分割

## 関連 Issue

- Closes #123

## 確認方法

1. ローカル環境を起動: `pnpm dev`
2. `/documents/new` にアクセス
3. フォームに情報を入力して送信
4. ドキュメントが作成されることを確認

## スクリーンショット（必要に応じて）

![スクリーンショット](url)

## レビュー時の確認ポイント

- [ ] フォームのバリデーションが正しく動作するか
- [ ] エラーハンドリングが適切か
- [ ] UI/UX が直感的か

## その他

特記事項があれば記載
````

### PR のサイズ

- **小さい PR** を心がけます（変更行数の目安: 200〜300 行以内）
- 大きな機能は複数の PR に分割します
- 1つの PR につき、1つの目的に絞ります

## レビュアーの責務

### レビューの優先度

レビュー依頼を受けたら、**24時間以内**にファーストレビューを行います。

### レビューの観点

#### 1. 機能面

- [ ] 実装が要件を満たしているか
- [ ] 仕様通りに動作するか
- [ ] エッジケースが考慮されているか
- [ ] エラーハンドリングが適切か

#### 2. コード品質

- [ ] コーディング規約に従っているか
- [ ] 変数名、関数名が適切か
- [ ] コードの重複がないか
- [ ] 適切な抽象化がされているか
- [ ] コメントが適切か（不要なコメントがないか）

#### 3. 設計・アーキテクチャ

- [ ] アーキテクチャに沿った実装か
- [ ] 適切な責務分割がされているか
- [ ] 依存関係が適切か
- [ ] 拡張性・保守性が考慮されているか

#### 4. パフォーマンス

- [ ] 不要な再レンダリングがないか
- [ ] データベースクエリが最適化されているか
- [ ] メモリリークの可能性がないか

#### 5. セキュリティ

- [ ] 入力のバリデーションが適切か
- [ ] 認証・認可が適切に実装されているか
- [ ] SQLインジェクション、XSS などの脆弱性がないか
- [ ] センシティブな情報がログに出力されていないか

#### 6. テスト

- [ ] 重要なロジックにテストが追加されているか
- [ ] テストがパスしているか
- [ ] テストケースが適切か

#### 7. ドキュメント

- [ ] 必要なドキュメントが更新されているか
- [ ] JSDoc コメントが適切か
- [ ] README の更新が必要な場合、更新されているか

## レビューコメントの書き方

### コメントの種類

コメントには以下のプレフィックスを付けて、意図を明確にします:

- **`[必須]`**: 必ず修正が必要
- **`[提案]`**: 改善の提案（修正は任意）
- **`[質問]`**: 理解のための質問
- **`[賞賛]`**: 良いコードへの称賛

**例**:

```
[必須] この関数は戻り値の型が定義されていません。明示的に型を指定してください。

[提案] この処理は共通化できそうです。utils/ に切り出すことを検討してみてください。

[質問] ここで `useState` ではなく `useRef` を使用している理由を教えていただけますか?

[賞賛] エラーハンドリングが丁寧に実装されていて素晴らしいです！
```

### 建設的なフィードバック

- **具体的**: 「良くない」ではなく、「〇〇の理由で△△にした方が良い」
- **丁寧**: 攻撃的な表現は避け、敬意を持って
- **教育的**: 理由や代替案を示す

**NG な例**:

```
このコードは間違っています。
```

**OK な例**:

```
[必須] この実装だと、〇〇の場合にエラーが発生する可能性があります。
以下のように修正することで、エッジケースにも対応できます:

（コード例）
```

### コード例を示す

改善提案をする際は、可能な限りコード例を示します。

```markdown
[提案] この部分は以下のように書き換えることで、より読みやすくなります:

\`\`\`typescript
// 現在
const status = user.isActive === true ? 'active' : 'inactive';

// 提案
const USER_STATUS = {
  ACTIVE: 'active',
  INACTIVE: 'inactive',
} as const;

const status = user.isActive ? USER_STATUS.ACTIVE : USER_STATUS.INACTIVE;
\`\`\`
```

## PR 作成者の責務

### レビューコメントへの対応

1. **すべてのコメントに返信**: 対応済み、または対応しない理由を明記
2. **質問には丁寧に回答**: レビュアーが理解できるように説明
3. **修正後の確認依頼**: 修正が完了したら、レビュアーに通知

### 対応方法

- **[必須]**: 必ず修正
- **[提案]**: 検討し、対応するか理由を添えて返信
- **[質問]**: 丁寧に回答

**返信例**:

```markdown
> [必須] 戻り値の型を明示してください。

修正しました！ c0mmit: abc123

---

> [提案] utils/ に切り出してみてはどうでしょうか?

検討しましたが、この機能は現在この画面でしか使用しないため、
今回は切り出さず、将来的に他で使われるようになったタイミングで
共通化する方針にしたいと思います。

---

> [質問] なぜ useRef を使用していますか?

DOM 要素への直接アクセスが必要なため、useRef を使用しています。
具体的には、フォーカス制御のために input 要素への参照を保持しています。
```

## マージの基準

以下の条件を満たした場合、マージ可能です:

- [ ] すべての必須コメントが解決済み
- [ ] 少なくとも 1 人のレビュアーが承認（Approve）している
- [ ] CI/CD がすべてパスしている
- [ ] コンフリクトが解消されている

## レビューのベストプラクティス

### レビュアー向け

1. **タイムリーなレビュー**: 24時間以内にファーストレビュー
2. **全体を把握してから**: コード全体の流れを理解してからコメント
3. **重要度を明示**: [必須]、[提案] などのプレフィックスを活用
4. **ポジティブなフィードバック**: 良いコードには称賛を
5. **学ぶ姿勢**: 新しいアプローチに対して柔軟に

### PR 作成者向け

1. **自己レビュー**: PR を作成する前に自分でレビュー
2. **小さい PR**: 変更を小さく保ち、レビューしやすく
3. **説明を充実**: PR の説明を丁寧に記述
4. **質問歓迎**: 不明点があれば、気軽に質問
5. **学ぶ機会**: レビューコメントを学習の機会と捉える

## 避けるべき行動

### レビュアー

- ❌ 攻撃的・否定的なコメント
- ❌ 根拠のない批判
- ❌ レビューの放置
- ❌ 個人攻撃

### PR 作成者

- ❌ レビューコメントの無視
- ❌ 説明不足の PR
- ❌ 巨大な PR
- ❌ コーディング規約違反

## GitHub の機能を活用

### Suggested Changes

軽微な修正は GitHub の "Suggested Changes" 機能を活用します。

```suggestion
const userName = user.name;
```

### Draft PR

作業中の PR は "Draft" として作成し、レビュー準備ができたら "Ready for review" に変更します。

### Reviewers の指定

適切なレビュアーを指定します。専門知識が必要な場合は、その分野に詳しいメンバーを指定します。

## まとめ

コードレビューは、チーム全体の成長とコード品質の向上に欠かせないプロセスです。お互いに敬意を持ち、建設的なフィードバックを心がけましょう！

不明な点があれば、遠慮なくチームメンバーに相談してください。
